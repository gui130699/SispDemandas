4. AUTENTICAÇÃO
====================================================================

Firebase Authentication: IMPLEMENTADO via Email/Senha.
Login: signInWithEmailAndPassword, mensagem genérica para falha.
Logout: signOut via AuthContext.
Recuperação de senha: sendPasswordResetEmail em LoginPage e UsersPage.
Criação pública: createUserWithEmailAndPassword.
Criação por admin: secondaryAuth cria conta com senha aleatória e envia reset.

Controle de sessão:
- onAuthStateChanged obtém User Firebase.
- onSnapshot em users/{uid} obtém o perfil.
- se perfil não existir, Protected redireciona ao login.
- se profile.active for falso, mostra BlockedPage.
- Rules usam profile.active == true; portanto inativação bloqueia operações
  de banco mesmo que a sessão Firebase ainda esteja autenticada.

Persistência: usa persistência padrão do Firebase Auth, não há configuração
explícita de persistência.
Tokens: não há token próprio nem gravação manual de token no localStorage.
Tema, não token, é salvo em localStorage.theme.
Senhas: não são armazenadas no Firestore/código. Senha pública transita pelo
SDK Firebase. O admin interno gera senha aleatória no cliente da secondaryAuth.

Riscos:
- Não há tratamento de erro no listener do perfil Firestore; uma falha de
  permissão/rede pode deixar loading ou perfil em estado pouco claro.
- A conta inativa continua autenticada no Firebase até logout; Rules mitigam
  dados, mas a UX não força signOut.
- Não há MFA, rate limiting visível, captcha ou proteção adicional.

10. CONSULTOR X EMPRESA
====================================================================

Modelo: companyIds:string[] no usuário. Não há coleção intermediária.
companyId existe no perfil para requester; consultant usa companyIds.

Comportamento atual real:
- Rules consultantCompany(companyId) verifica se demand.companyId está em
  profile().companyIds.
- leitura de demanda para consultor é permitida para TODAS as demandas das
  empresas listadas, inclusive demandas atribuídas a outro consultor.
- update usa assignedOrAvailable(resource.data): permite se a demanda é do
  consultor atual OU está sem consultor.

Um consultor pode ver empresa não autorizada?
IMPLEMENTADO COM RISCO CRÍTICO: a regra consultantOwnCompanyLink permite que
o consultor atualize a própria lista companyIds sem validar empresa, aprovação
ou vínculo. A UI Dashboard exibe todas as empresas ativas para “Vincular
empresa”. Após isso, consultantCompany torna a empresa “autorizada”.

Regra responsável e interpretação:
consultantOwnCompanyLink só restringe os campos modificados a companyIds e
updatedAt; não restringe quais IDs entram na lista.
consultantCompany confia integralmente nessa lista. Portanto o isolamento
multiempresa é quebrado por auto-vinculação.
